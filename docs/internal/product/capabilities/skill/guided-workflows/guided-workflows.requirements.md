## Authority and purpose

The owner's discussions and Q&A are recorded in the recon. The later explicit EXECUTE request and eight consolidated answers accept this implementation scope, including optional design-PR preference, provenance warnings and conventional-commit defaults. These requirements define observable outcomes; actual delivered scope and limits are recorded in the execution verification.

Users should be able to start Stavel, adapt its conventions and carry a feature from exploration through verified execution with durable context and useful defaults. Both terminal users and coding agents are audiences. Existing [package requirements](../../../contracts/framework/framework.requirements.md) remain current authority; these additions supplement them when accepted.

## Required mechanisms and preserved contracts

Retain inspect-before-questioning, cited decisions, complete alignment before adoption generation, explicit portable catalog membership, hash-based plan preflight, containment/symlink/collision refusal, differing-file preservation and journal recovery. Semantic assessment belongs to the agent/reviewer; deterministic checks cannot certify philosophical correctness. Natural-language intent must resolve into explicit scoped choices rather than invisible prompt memory.

CLI and agent presentations share decisions, effective configuration and mutation services. A customization is an owned source record; rendered help/tracker/instructions are derived views with provenance. Implementation of these mechanisms must be demonstrated independently of matching class or file names.

## Constraints and non-goals

Keep Node-based optional tools, mdcomposer's separate canonical implementation, language-agnostic policy and existing supported environments. Preserve current Stavel identities and legacy refusals. Package version, persistence schema and default-profile versions are separate decisions; this packet does not select a release number.

No npm publication/release pipeline, deployment, application runtime changes, automatic installation of target dependencies, new AI-provider integration or global skill replacement is authorized here. Java/Python integrations remain contribution opportunities, not implied implemented checkers. Shared extension registries/distribution infrastructure are follow-up work unless separately selected.

Use existing canonical owners where present. This feature's user problem is captured here instead of creating a separate product document. CLI interaction, backend services, local persistence and architecture are covered in the [design](./guided-workflows.design.md); separate visual UI, tenant IAM and cloud-infrastructure packets are omitted for this local toolkit. Revisit those choices if scope changes.
